## 1. Memory ownership

- Walrus Memory account is **operator-owned** for MVP.
- The CEO owns the Aquahab company profile and controls company data through the app.
- Agents do not own wallets or memories.
- CEO-owned, self-custodial memory is **Phase 2**.

## 2. Memory lifecycle

- **Manual renewal only.** No automatic renewal in MVP.
- Lifecycle states: `active`, `expiring_soon`, `expired`, `renewal_required`.
- An expired memory is shown as expired. It is never silently removed.
- Forgetting is not a lifecycle state. It is recorded as `forgottenAt` (a separate field), so the four states above stay exact.

## 3. Agent execution

- **On-mission only.** No daily or weekly scheduler in MVP.
- The CEO must approve **preference**, **feedback**, and **decision** memories before they are stored.
- **Outcome** memories (completed-task results) may be stored automatically after validation (see §3.1).

### 3.1 Automatic outcome storage: validation rule

An outcome memory is written without CEO approval only when all of these hold:

1. The task reached `review` through a successful LLM call. It did not become `blocked`.
2. The output has every section required by the template's output contract.
3. The output is non-empty and under the length limit (proposed: 8,000 characters).
4. The redaction layer found nothing to block.
5. The outcome summary is generated by the orchestrator (max 500 characters) from the output. The full output is never stored.
6. The memory quota (count and bytes) has room.

If any check fails, no outcome memory is written. The task shows which check failed. A failed outcome check never blocks the CEO from reviewing the task.

An auto-stored outcome shows an "Auto-saved" badge in the Vault. The CEO can forget it or supersede it.

## 4. Agent budget

- LLM and compute budget: **USD cents**.
- Memory quota: **count and bytes**.
- Task quota: **count**.
- Tool quota: **count**.
- Per-task LLM cap: **USD cents**.
- **Aquahab-managed LLM key** for MVP. BYOK is **Phase 2**.

Budget values in demo config are proposals to confirm before the demo. They are not product decisions.

## 5. Agent permissions

- Agents may **propose** memory candidates.
- **Only the orchestrator calls Walrus `remember()`.**
- Permissions are enforced by Aquahab, not by Walrus.
- The Walrus delegate key is account-wide and **stays server-side**.

## 6. Agent creation

- MVP supports **five fixed roles** with **fixed desks**: One (chief of staff), Researcher, Builder, Lofi (creative), Hippo (operations).
- The CEO may **enable, disable, pause, edit strategy, and fund** each agent.
- **No arbitrary agent creation** in MVP.

## 7. skills.md

- **Untrusted** configuration input.
- **Size-limited**, **redacted** before use, and **versioned**. Each saved version has a version number and a hash.
- **Never automatically stored as memory.**

## 8. MVP decisions, v2.2 (2026-10-27)

These decisions override earlier drafts in every product doc.

1. **Ask the Vault is Phase 2.** The MVP has no Ask control, no Ask route, and no Ask acceptance criteria. Recall-based sourcing for memory use stays in MVP through the Mission Result and Agent Detail views.
2. **Onboarding step 1 is "Start demo CEO session".** No wallet is connected in MVP.
3. **Google sign-in via Enoki zkLogin is Phase 2.** Confirmed by the product owner. In Phase 2 it is the app sign-in: a Google account maps to one CEO identity and one company. It does not change memory ownership. The operator account keeps the blobs until wallet ownership and self-custodial memory (Phase 2 list below) exist.
   - Before Phase 2 planning, verify the Enoki setup. The MemWal research (`docs/reference/enoki-connect-requirements.md` in the MemWal repo) says Enoki Connect must use Enoki's default salt, and the app's origin must be allowlisted in the Walrus Memory Enoki app. Sponsored transactions are a separate check.
4. **Tatum brand palette and Poppins are Phase 2, only after written permission from Tatum.** Until then the active tokens are the Aquahab deep-sea palette (DESIGN.md Appendix A).
5. **Typography for MVP is Geist Sans and Geist Mono.** Geist Mono covers data values such as IDs, epochs, and cents.

### MVP scope, final

- Demo CEO session (no wallet, no Google sign-in).
- Operator-managed Walrus Memory account. The CEO owns the company profile in the app.
- On-mission agents only. Five fixed roles.
- Manual renewal only.
- Aquahab deep-sea UI with Geist Sans and Geist Mono.

### Phase 2

- Ask the Vault.
- Wallet ownership and self-custodial Walrus memory.
- Google sign-in via Enoki zkLogin.
- Scheduled agents.
- Tatum brand palette and Poppins (after written permission).

## 11. Total Recall refinement, v3.0 (2026-11-03), proposed for the product owner

Proposed by the backend owner with the backend PR. It overrides §1–§10 where they conflict once the product owner accepts it. Rationale and sources: the "Make Aquahab the crew that remembers" refinement brief shared on 2026-11-02.

**The job.** Aquahab is a 3D office whose crew remembers where you left off on each of your real projects. The "CEO runs a company of AI agents" framing stays as the presentation, not the job.

1. **Rooms replace missions.** Each real project is a room, and each room is exactly one Walrus Memory namespace, `aquahab:room:<slug>` (an HMAC alias for a private project, because namespace names are public in Blob metadata). One more namespace, `aquahab:ceo`, holds the CEO's preferences and feedback across rooms.
2. **Scheduled agents move from Phase 2 into the MVP.** They are the core loop:
   - a morning brief at the CEO's time (Telegram and app), one section per crew member, every line citing the Walrus blob ids it came from;
   - an evening debrief: the crew asks how the day went, proposes memories, and files only the ones the CEO keeps (the PR #2 review panel is this approval step);
   - quick capture at any time: `d:` decision, `f:` failure, `n:` next, `done:`, `l:` learned, `due:` deadline, `s:` story, `p:` preference.
3. **Employees are delegate keys.** One, Researcher, Builder, Lofi, Hippo and the Walrus Keeper are each an Ed25519 delegate key on the Aquahab MemWalAccount, labelled with their name on-chain. Hiring is `add_delegate_key`, firing is `remove_delegate_key`, signed by the CEO (the account owner). This replaces "only the orchestrator calls remember" (§3): the **Keeper is the only write path**, but each memory is signed by the key of the member who files it, so authorship is on-chain (`memwal_agent_id` in Blob metadata).
4. **Memory types live in the memory text** (`[type][room][date][by:agent] …`), because recall has no tag filters. Types and filers: decision, next → One; failure, done → Builder; learned → Researcher; deadline → Hippo; story → Lofi; preference, feedback → Keeper.
5. **The office is drawn from Sui through Tatum.** Who works here (the MemWalAccount's delegate keys), the hire/fire history (DelegateKeyAdded/Removed events), which memories exist and who filed each one (Walrus Blob objects and their metadata) are read through Tatum's Sui gateway (native gRPC and GraphQL). Tatum moves from Phase 2 (§8.4 palette aside) into the MVP, because it is named in criteria worth 60% of the score.
6. **Mainnet only for the submission.** The SDK's in-memory mock (`MEMORY_MODE=mock`) exists for UI development and tests; the server refuses to start with it in production.
7. **LLM:** one provider through the Vercel AI SDK and AI Gateway (Claude Sonnet for briefs and debriefs, Claude Haiku for classification), with deterministic fallbacks so the loop never stops. Tatum is not an LLM provider.
8. **Cut from the MVP:** missions with budgets and governance, manual renewal (the SDK has no renew; live memories are stored for 15 Walrus epochs, about 30 weeks), Aqua City, Ask the Vault (`/ask` over recall covers it), the separate Company Briefing (the morning brief replaces it), Agent Payments.
9. **Supersede, never forget.** The TS SDK has no `forget()`, and the REST forget clears a whole namespace. A correction is a newer memory tagged `[supersedes:<blob_id>]`.
10. **One CEO per deployment.** The office is public to read (judges see the real rooms, crew and receipts). Writes need the CEO session, opened from the Telegram bot's `/web` link.

Display names and role titles from §10 are unchanged. Internal ids add `keeper`.

## 12. Telegram bot: buttons first, v3.1 (2026-11-05)

Spec: `docs/features/telegram-bot.md`. This section changes how the bot asks for input. It does not change §11.

1. **New room is a three-step flow.** ＋ New room asks for the name, then the goal (Skip goal), then the times (Use default 08:30 · 21:00, or type `HH:MM HH:MM`, optionally with `private`). The typed `/new Name | goal | times` stays as a shortcut.
2. **Times are picked, not typed.** `/times` with no arguments and the ⏰ Times button show preset pairs and a "Type my own" option. The default is 08:30 · 21:00, the same value `createRoom` uses.
3. **Capture uses the §11.2 prefixes.** `d: f: n: done: l: due: s: p:` are the canonical way to file a note. The capture buttons are a shortcut, and onboarding says the prefix works too.
4. **One command reference.** `/help` and "How to use" show the same reference, built from one list of capture types. `/skip` is advertised with the other commands. `/room` still works but is not advertised.

**Why:** the CEO should not need to know the `|` syntax or the prefixes to get started. Buttons lead, and typed syntax stays for speed.

**How to apply:** new Telegram prompts go through the `Pending` state with a button for every optional field. Do not add a new typed-only option without a matching button.

## 13. The office comes alive, v3.2 (2026-11-06)

Spec: `docs/features/hq-scene.md`, section "Current build". This section overrides §9 where they conflict.

1. **Walking agents are in the MVP.** §9 listed walking agents as Phase 2. The CEO asked for the crew to move around each desk, so they roam within a radius of their desk and keep clear of the office objects.
2. **Status and task are not shown.** The server does not report agent status or current task. The labels show the title and the memory count. The old mock task text is removed.
3. **`mock.ts` is removed from the web app.** The scene, the agent tabs and the drawer read `/api/crew` only.
4. **Object captions come from the geometry.** Names are added once each object is identified.

**Why:** the labels must not show data the server did not return. The crew should look alive without pretending to know more than the server does.

**How to apply:** new scene labels read from the API. Do not add a status or a task to a label unless the server reports it.

## 14. Contractor writes go straight to Walrus, v3.3 (2026-11-08)

Code: `server/scripts/contractor.ts` (PR #29). This is an exception to §11.3, which says the Keeper is the only write path.

1. **A contractor is a labelled key on the payroll.** Claude Code gets its own delegate key, hired and fired on-chain by the owner (`pnpm account hire-contractor` and `fire-contractor`). Its key lives in `server/.env.contractor.local`, which is git-ignored and never deployed.
2. **Contractor writes bypass the Keeper.** `pnpm contractor remember` writes a true line straight to Walrus, signed by the contractor key. The CEO's approval is the hire, and firing the key ends it.
3. **Preferences and feedback stay with the CEO.** The contractor cannot file `p:` or 👎 feedback.
4. **The contractor's memories count** toward the room total, because the Keeper's count reads the Walrus listing.

**Why:** Claude Code works on the project outside the server, so routing its notes through the server would put the server in the middle of a Telegram-free workflow. The on-chain key keeps authorship visible.

**How to apply:** a new write path needs its own key on the payroll, its own line in this section, and a CEO hire. Do not let other clients call Walrus without one.
